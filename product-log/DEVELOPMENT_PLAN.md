本计划依据[PRODUCT](../PRODUCT.md)、本轮用户的 F01–F14 缺口核对及[ISSUES](ISSUES.md)，替代 PLAN-001 从零初始化的执行顺序。沿用现有实现和 DEV-001～DEV-012 历史任务，不重建项目。实际进度、验证结果、当前可执行项只维护在[PROJECT_LOG](PROJECT_LOG.md)；此处是任务范围、依赖和验收，不是第二份进度账本。

本轮授权是规划。开发、修复和运行任务不会因写入本计划而自动开始；不修改业务代码、数据库或既有未提交成果。最新改版方向单列，已确认的三项个人扣款及体验要求已同步PRODUCT；其余歧义在ISSUES收口后实现。

## 4. 实施顺序与可并行范围

建议首批先交付 GAP-001 → GAP-003/GAP-004 的教师基本闭环；GAP-002 权限与 GAP-008a 任务基础同时推进。GAP-008b 是业务接入子项：费率重算依赖 GAP-006，月度接入依赖 GAP-010，备份接入依赖 GAP-015；这些业务包只依赖已完成的 008a，不能反向等待整个 008b。GAP-009 的多图报销可在契约收口后提前进入，GAP-010 按三项扣老师个人账户的已确认规则先做契约与历史兼容，再实现统一办理。

随后按依赖交付 GAP-005～007 管理配置和重算、GAP-010～013 财务；GAP-014 先基于已存在事实做读模型和组织看板，再随财务类型补齐。GAP-015 任务壳及下载授权可提前开发，但完整性通过必须等所有新增业务源覆盖。GAP-016 的回归清单和风险审查贯穿每包，真机与最终用户验收集中收口。

不是把所有后端做完才做页面。每包先稳定数据/权限/错误/版本契约，前后端随即并行；每包以实际用户操作及服务端结果收口。第一阶段结束示例：新老师登录→发送→获授课身份的老师接收选场地→录费→看合法收入→申请提现→财务办理，全程无开发者手填数据库补步骤。发送身份规则按P41先收口。

不据旧“两周”期望虚报剩余工期。先完成入口与教师闭环，用实际速度评估剩余；资金改版、完整导出和真机分别给估算，不把等待业务决定/设备的时间混为开发已完成。

## 5. 接口与迁移约定

- 每包先列角色、页面、读/写接口、字段范围、状态、版本冲突和失败结果，再编排实现。公共契约由一个负责人合并；现有可用服务不重写。
- 管理配置必须有持久化版本及真实HTTP/启动装配；内存类、常量、演示预置和孤立函数不能作为后台完工证据。
- 涉及入账的命令绑定同一业务键、原版本、真实账户和来源；页面超时保留可安全重试命令，不因再次点击换键重复入账。旧会话响应不能污染新角色。
- 月度一键执行的建议技术边界：同一老师同月本次三项作为原子操作；重复或超时返回同一结果，冲回保留原分项。若后续增加全名单批量，必须逐行显示真实结果，不以部分完成显示全部成功。这是按已确认P42制定的实现方案，具体事务设计仍需验证。
- 新旧工资/福利模型以关联版本兼容，不能从旧待办再次扣钱，不能覆盖旧确认、原件和冲回。报销新入口不重绑旧凭证，不通过复制同一文件伪造双槽齐全。
- 关系、费率发布要绑定预览版本与影响集合，拒绝过期预览；本财年规则回算只调整相关差额，不清掉工资、报销、提现、人工调整等独立账务。
- 每个新增或变化的持久模型同时更新导出schema、事实/派生映射及非空备份样例；不得在最后靠补零伪造缺失业务。
- 迁移编号由主Agent在接手时统一分配，先核对其他分支已占用编号；使用隔离合成数据库。旧数据恢复与代码回滚分别设计，不宣称回退代码能撤销已入账事实。

## 6. 多 Agent 文件归属与验收责任

同时最多采用主Agent加三个子任务；具体人员随阶段调整，不要求所有任务同时开工。

| 责任 | 唯一写入范围 | 交接结果 |
|---|---|---|
| 主Agent / 集成 | PRODUCT、ISSUES、PROJECT_LOG；公共contracts/client、HTTP总分发/API启动、迁移编号由主Agent指定单一写入人 | 业务边界、稳定接口、合并、实际验收、日志与commit |
| 后端Agent | 当包独立服务、已分配迁移和后端测试；未获分配不改共享总入口 | 持久行为、权限、失败/重试与真实PG证据 |
| Web Agent | 当包独立面板及Web测试；app.tsx同阶段只交一名负责人 | 从导航进入的完整交互及手机/电脑适配 |
| 小程序Agent / 独立审查Agent | 实现阶段为对应小程序面板；关键包结束后释放槽位给未参与实现的审查者 | 同业务契约、小程序构建；独立审查资金/权限/迁移及缺口 |

各Agent必须保护别人修改，同文件同阶段单写入。主Agent不以子Agent自报代替核验；后端稳定后前端并行，资金或关系变更的关键包安排独立审查。没有AppID/真机证据时明确标未验证。

## 7. 每包完成与整体完成标准

每包必须同时具备：可达入口 → 合法读写 → 持久记录 → 正确账务/范围 → 可查历史 → 异常恢复 → 两端适配。无写操作的看板按其查询范围验收，不人为增加写功能。

验证按风险执行：

1. 先跑受影响的计算、权限、客户端或组件聚焦检查；入账、迁移、关系和配置版本变化必须在隔离真实PostgreSQL验证事务、并发、重复、回滚及历史。
2. 业务代码交付执行 `npm run check`、`npm run db:check`、`git diff --check`；Web执行 `npm run build:web` 与对应合成浏览器场景；小程序执行 `npm run build:miniapp:dev` 并记录开发者工具/真机是否实际执行。浏览器现有入口为 `ALLIANCE_SYNTHETIC_E2E=1 npm run test:browser --workspace @teaching-research-alliance/web`，具体服务和资料按测试要求隔离配置。
3. 每个可见菜单都要点击；至少一个业务从用户操作到HTTP、数据库/账本和历史查询贯通。检查正式API装配，不只跑demo。跨端写读一致、角色切换字段清理、超时/并发冲突按场景验证。
4. 主Agent复核独审意见、实际证据及未执行项，更新唯一日志；仅暂存本包文件，提交标题含 `[xiaosi]` 和稳定任务编号。必需检查失败则修复或明确checkpoint，不能标完成。
5. 纯文档规划执行覆盖、依赖、引用和差异检查，不以运行全业务测试验证文字。

整体完成要求 F01–F14 每项有需求条款、后端/API、Web入口、小程序入口、权限及正反例证据映射；所有必须业务门禁通过、用户操作可演示。工程完成、真机验证、用户验收及生产发布分别记录。AppID、真实资料、费用或部署条件未具备时只暂停对应事项；本次规划本身不授权这些外部动作。
