# PLAN-001｜开发实施计划

本计划依据[最终需求](../PRODUCT.md)、[技术设计](../TECHNICAL_DESIGN.md)与[问题登记](ISSUES.md)，采用 `teacher-product-development` 的任务拆分、连续推进和独立审查方式。计划说明执行顺序，实际进度和验证证据只维护在[执行日志](PROJECT_LOG.md)。本轮交付开发规划；以下开发任务尚未执行，不代表应用已经可运行。

## 1. 交付目标

首版完成 F01–F14：教师能推荐与接收学生、登记周费用、查看个人收入；各职责在授权范围内管理和查看；总部财务处理单据、工资和扣费；管理员维护人员与费率并导出完整备份。微信小程序、手机网页、电脑网页使用同一业务和账务结果。

按“先证明算得对、账户分得清，再逐步接齐流程与看板”的顺序交付。小程序为主要业务端，第一条闭环就同时接入小程序和响应式网页，避免最后才发现端能力或交互不适配。首个演示仅是增量验收点，不缩减完整首版范围。

当前仓库只有需求、设计与审查文档，没有可运行的应用、数据库迁移或自动化测试。沿用现有 TypeScript、Taro/React 小程序、React 网页、NestJS API、PostgreSQL 技术基线；具体依赖版本在工程初始化时验证兼容并锁定，不在本计划里宣称已经安装或可运行。

## 4. 第一条演示怎么验收

使用合成规划师、规划导师、授课教师、组长、教学指导导师与组织/财务对象。固定普通周、既定关系和授课教师本人已创建的自有场地，先验证固定输入的账务闭环；全部正常场地选用与管理员指定关系变更范围在后续场景覆盖。

1. 管理员配置期间和初始比例；规划师推荐学生，授课老师接收并选择本人场地。
2. 教师录入本周累计 1,000 豆，当月净额落在零浮动档；系统按有效配置计算并入账。
3. 初始比例下，规划师 80、规划导师 20、组长 60、教学指导导师 70、场地 0、介绍方校区 20、平台财务 20、分区财务 10、授课教师 720，共 1,000 豆。各项进入已配置的合法账户；管理费不进入校长个人账户。
4. 将同笔累计值改为 1,200 豆，且净额仍在零浮动档：新分配依次为 96、24、72、84、0、24、24、12、864。仅入账合计 200 豆的差额，不重复新增 1,200 豆；两端刷新看到同一计算版本。
5. 重复提交、同时编辑、缺少必要收款对象、越权读数据分别验证；不得重复加豆或留下部分成功账务。

演示金额另用独立算例校验，不能以页面上出现预置数字冒充后端结算成功。正负动态、档位跳变、退款和关系变更由后续完整用例覆盖。

## 5. 必须从第一阶段坚持的实现边界

- **身份和钱分别建模**：自然人账号、当前职责、业务范围、个人/业务/场地账户分开。取得看板权限不等于取得提现、费率修改或他人余额权限。
- **保留历史且可核对**：费用、费率和关系有版本；重算追加差额。先固定受影响记录、校验完整新结果，再原子发布账务和计算版本；异步处理不能把旧余额标成本次已更新。
- **并发与重试是业务正确性的一部分**：提现与重算锁定同一来源账户，退款与费用修改避免重复冲回，任务重试不重复划拨。常规新增/改错影响的整月计算需验证推荐方和授课方两侧。
- **退款有独立时序**：批准当次只冲选中周费用的最新有效分润；以后正常新增/改错按排除已退款的双方金额重算其他有效费用。不能因重算恢复退款，也不能用普通付款再扣一次。
- **权限在服务器生效**：所有比例修改归管理员/开发者；按当前职责过滤查询、嵌套字段与导出；个人视角无工资字段。校长不因管理校区获得校区账户资金所有权。
- **验证用例从需求独立推导**：金额到分、15 档边界、动态负值、跨月/跨年、角色切换、撤销与并发均有确定期望；历史文档中的算例检查不算应用测试已通过。
- **备份从模型开始考虑**：保留稳定关联、历史版本、附件索引和原件，避免最后才补无法追溯的数据；Excel 可读备份与数据库恢复分别验收。

## 7. 多 Agent 分工与交付节奏

主 Agent 负责计划、公共数据/接口契约、迁移整合和最终验收；契约稳定后最多并行安排三个明确工作包。建议分为后端业务、纯计算/账本、两端页面；按当前依赖切换为财务、备份等工作包，避免所有模块同时开工。

每次任务给出文件所有权、输入输出、依赖和验收命令。数据库迁移编号、公共 OpenAPI 与共享金额类型同一阶段只有一名写入负责人。子 Agent 不覆盖其他人的修改；审查者只读审查，主 Agent 结合实际命令与交互核验处理问题。

开发使用功能分支。每个可独立描述的工作包完成后：聚焦验证 → 独立审查关键风险 → 更新执行日志 → 检查暂存范围 → 创建含 `[xiaosi]` 的提交 → 按已有授权同步 GitHub。PR 创建时关联到当前任务。不可运行的中断点只能标为 checkpoint，不伪装合格交付。

原有“两周”作为首版交付期望。启动后先以 A/B 阶段实际完成速度估算剩余工作，不在没有运行证据时承诺全功能、真机、微信审核同时完成。每个阶段提供可操作演示和剩余限制；技术验证通过后连续推进已授权工作，只有产品决定或生产外部条件阻塞相关任务。
