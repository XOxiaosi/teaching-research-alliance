# 全量 Excel 备份导出技术契约

## 1. 目的、范围与非目标

本文为 F14“管理员全量 Excel 备份导出”提供实现和验收契约。它补足 V1.6 的 F12 中“管理员可查看和导出所有表”未定义的范围、完整性和安全要求。

- **使用者与入口**：只有管理员可在手机或电脑的管理端网页进入“数据备份与导出”，发起异步备份、查看任务状态并下载成功文件。生成在服务端完成。微信小程序是主业务端；管理端是否也在小程序提供同一入口可在界面设计时按安全性与操作体验决定，但不能削弱已确认的网页管理端能力。
- **全量备份**：按某一确定时点，导出所有业务数据、历史配置和支持理解关联与计算所需的元数据。它不受看板“金额为 0 隐藏”规则影响。
- **按期报表**：按月、年、组织或人员筛选的可读报表，是另一种导出类型；只能包含筛选结果，不能被称为全量备份。
- **非目标**：本文件不生成 `.xlsx`、不接入真实数据，也不提供 Excel 批量导入或恢复生产库的能力。数据库物理灾备、对象存储灾备和恢复演练仍是独立能力。

## 2. 导出类型与管理员操作

| 类型 | 选择条件 | 内容 | 成功条件 |
|---|---|---|---|
| 全量备份 | 无业务筛选；系统记录 `asOf` 时点 | 第 3 节全部工作表、清单和校验信息 | 所有数据集来自同一快照，`manifest` 校验通过 |
| 按期报表 | 月/年、校区、分区、人员等已授权筛选 | 所选报表及其筛选说明；可含必要汇总和明细 | 与界面筛选口径一致，不能替代全量备份 |

操作采用异步任务：管理员在手机或电脑管理网页提交请求后得到任务编号；服务端固定快照、生成文件、执行备份完整性校验，再显示“可下载”。失败任务保留错误码、失败阶段和重试条件，不产生“成功”文件。重新下载同一成功任务不重新取数；重新生成必须创建新的快照和新任务。

## 3. 全量备份的数据范围

每份全量文件必须含 `00_manifest` 工作表和下表数据。业务表应输出稳定的内部 ID、业务显示名、创建/更新/删除状态、创建人/更新时间与版本号；显示名改变不能破坏关联。原始字段、审计 JSON 与长文本均须无损保留，不能仅导出看板可见列。

| 工作表或文件组 | 最低必须内容 | 目的 |
|---|---|---|
| `00_manifest` | 第 4 节字段、工作表清单、各表行数、逻辑摘要、总金额、时区、文件组编号 | 证明本次导出是什么及如何核验 |
| `01_组织与权限` | 组织/校区/分区、人员、角色分配、人员与校区/分区/收款对象关系、角色历史 | 解释数据范围与归属 |
| `02_表1_教师信息` | 表1所有非秘密原始字段、昵称变更映射、软删除和历史版本 | 还原主数据语义与关联 |
| `03_表2_业务流水` | 表2所有字段、接收状态与业务状态变化、周流水/结算月份、源记录版本 | 追溯费用来源 |
| `04_分配明细` | 每笔流水的 `F`、费率、每一分润对象、金额、授课老师剩余、计算版本、当时匹配的关系和配置版本 | 使表3/表7可逐笔复核，不能只导出汇总 |
| `05_表3_月度收入` | 表3原始/已发布汇总、期间、汇总版本和状态 | 复核月度口径 |
| `06_表4_财务单据` | 三类单据全部字段、审批状态、有效性结果、状态/审批历史与关联附件清单 | 复核收入和支出调整 |
| `07_表5_工资奖金` | 工资、10 项奖金、项目名称在该行生效的版本、历史名称与调整记录 | 解释工资总和 |
| `08_表6_扣费` | 医社保、10 项扣费、项目名称在该行生效的版本、历史名称与调整记录 | 解释扣费总和 |
| `09_表7_费用结算` | 月/年/累计结算快照、各组成项、余额、结算状态和版本 | 复核最终余额 |
| `10_表8_绩效配置` | 默认比例、按接收方配置、有效时间、操作人、历史版本、复制/批量操作来源 | 解释分配规则的时间点 |
| `11_费率与系统配置` | 基础费率、抬升区间、执行状态、上限、项目名称、结算周期和所有历史配置版本 | 解释动态费率和历史计算 |
| `12_账务调整与审计` | 更正/冲销/关账重算记录、导出任务、登录外的管理操作审计、审批操作审计、执行人和时间 | 防止只看当前值而丢失变更轨迹 |
| `13_附件清单` | 附件 ID、所属业务 ID、文件名、介质类型、大小、校验和、存储状态和受限访问标识 | 使单据附件可被追溯；二进制原件不嵌入 `.xlsx` |

“删除”不得等同于从全量备份省略：软删除、撤销、拒绝、关闭、历史版本和零金额行均须导出，并以状态列说明。页面为了易读而隐藏零金额项目时，仍须保留机器可读原始行和金额字段。

### 业务异常保留原则

全量备份复制的是某一时点的真实已存数据，不是“把数据修正后再导出”的报表。配置缺失、业务金额不平、历史悬空引用、计算差额、旧版本字段不完整和其他业务校验异常，都必须原样导出；同时在 `12_账务调整与审计` 或独立 `14_业务异常` 工作表写出异常编号、涉及记录 ID、规则版本、发现时间和说明。

无效、拒绝、作废等业务状态记录同样保留；正常发生的状态本身不等于数据损坏或计算异常。

导出程序不得自动补数、重算覆盖、合并、删除或隐去异常行。备份内容完整不等于业务计算正确：业务校验状态与报表汇总核对状态独立记录，不能因业务异常使全库备份缺行或失败。

### 不导出的秘密与敏感字段

- 密码哈希、密码重置令牌、登录会话、API token、私钥、数据库连接串和任何密钥一律不导出。
- 设计要求管理员获准导出的手机号、银行卡号、开户行、收款户名、发票号等业务字段按原始文本保真；真实敏感字段的授权范围仍须按 D16 确定，下载、失败和撤销均写入审计记录。
- 卡号与手机号均以文本列保存，不能转为科学计数法、自动去前导零或按公式计算。是否可向非管理员导出、是否需要脱敏及保留期限仍受 PRODUCT 的 D16 约束。

## 4. 快照、清单与一致性

导出任务开始时建立只读一致性快照，所有工作表只能从该快照读取。快照结束后新增或变更的数据进入下一次导出，不能混入当前文件。

`00_manifest` 至少包含：

| 字段 | 含义 |
|---|---|
| `backup_id`、`export_job_id`、`file_group_id` | 本次导出与多文件组的唯一标识 |
| `export_type`、`schema_version`、`application_version` | 导出类型和字段解释版本 |
| `as_of`、`timezone`、`snapshot_id` | 固定数据时点、IANA 时区与一致性快照标识 |
| `requested_by`、`requested_at`、`authorization_scope` | 谁在什么权限范围内请求；不记录密码或 token |
| `filters` | 机器可读筛选条件；全量备份显式为“无业务筛选” |
| `sheet_name`、`part_no`、`row_count`、`min_id`、`max_id` | 每个工作表/分片的覆盖范围与行数 |
| `logical_digest`、`total_amounts`、`reference_check_result` | 按稳定排序和规范化值计算的逻辑摘要、金额合计和引用检查结果 |
| `generated_at`、`generator_version`、`backup_status` | 生成时间、程序版本和备份完整性状态 |
| `business_validation_status`、`report_reconciliation_status` | 业务异常汇总状态、报表汇总核对状态；二者不决定是否复制原始行 |

导出完成后，服务端生成并随文件组提供只读 `package-manifest.json`，其中列出每个 `.xlsx` 的文件名、字节 SHA-256、文件大小、工作簿逻辑摘要和全组必备分片；服务端任务审计也保存同一清单，供离线留档时核验文件组是否完整或被改动。工作簿内保存的是各数据集的 `logical_digest`，不把整份文件哈希写回自身，以免形成自引用循环。时区必须使用系统配置的 IANA 名称，并同时作用于 `as_of`、日期时间显示和期间边界；上线前固定该配置，不能由浏览器时区决定。

## 5. Excel 文件格式与大数据策略

Microsoft 规定单个工作表最多 1,048,576 行、16,384 列，单元格最多 32,767 个字符，且数字只有 15 位精度；因此导出不能依赖一个无限大的工作表，也不能把身份证明、精确金额或超长业务资料交给 Excel 自动处理。见已核实可访问的 [Microsoft Excel specifications and limits](https://support.microsoft.com/en-us/excel/excel-specifications-and-limits)。工作表名称还不得超过 31 个字符或含非法字符，见 [Microsoft Rename a worksheet](https://support.microsoft.com/en-us/excel/rename-a-worksheet)。

- 每个工作表最多写入 1,000,000 条数据行（另加标题）；超出时按稳定主键顺序拆为 `03_表2_业务流水_001`、`_002` 等分片。文件整体达到服务端配置的大小或生成时限时，拆分为同一 `file_group_id` 的多个工作簿，每一份都有完整 `manifest`。
- 后台按游标分页读取并流式写出，禁止先把全量记录加载到服务端内存。若技术栈采用 Node.js，ExcelJS 的官方仓库提供 streaming XLSX writer；选型和版本锁定时再以其 [官方文档](https://github.com/exceljs/exceljs#streaming-xlsx) 验证兼容性。
- 文本型 ID、手机号、银行卡号、昵称、发票号、精确金额和比例均以文本写入。金额必须提供 `*_exact_decimal`（不舍入的机器精确十进制文本，附币种与源精度）和 `*_display`（供阅读的文本）；若 D12 确定了最小货币单位，可另加 `*_minor_unit`，但不能替代源精确值；不在文件中放依赖 Excel 的业务公式。金额精度和舍入仍遵循 D12。
- 所有业务文本显式写为 XLSX 字符串单元格，尤其首字符为 `=`, `+`, `-`, `@` 时禁止写为公式类型，也不插入会改变值的前缀；在 `manifest` 标明 `text_encoding=xlsx_string_v1`。读回值必须与源文本一致，并核验不存在来自业务输入的公式单元格。
- 单元格超过 32,000 个 UTF-16 代码单元的审计 JSON、备注或其他原始长文本，主记录保留 `long_text_ref`，完整文本写入 `14_长文本分片`：`long_text_ref`、源表、源记录 ID、字段名、`part_no`、`part_text`。每片控制在 32,000 个 UTF-16 代码单元内，边界不拆开代理对；按 `part_no` 顺序拼接必须逐字符等于源值；不得截断、摘要或以下载链接替代。若不能新建该工作表、写入任一分片或写入后重组校验失败，备份任务失败，不能降级为截断成功。
- 工作表名、列名、枚举值和字段版本需由导出 schema 注册表统一维护。`sheet_id` 必须是 31 字符以内的合法且唯一技术名，完整中文逻辑名写入 `manifest`；名称冲突或无法分配合法新工作表时任务失败，不能截断名称后覆盖另一工作表。新增列为向后兼容追加，删除或改义必须提升 `schema_version`。

## 6. 生成、下载与留存安全

1. 服务端在创建任务和开始生成前各校验一次管理员角色；生成过程若权限被撤销则标记任务失败并删除未完成临时文件。
2. “下载”必须经过受控服务端端点：在响应开始前再次校验权限、任务所有权/管理员范围、文件状态和一次性下载令牌。不能把对象存储的长期裸链接交给浏览器。
3. 下载流开始后，系统持续检查撤销标记；角色被撤销时中止尚未完成的传输并审计“已中止”。已经发送到客户端的字节无法收回，此限制必须如实记录。
4. 下载令牌仅可使用一次，并使用短有效期。**建议**有效期 15 分钟；该数值不是当前已确认的保留或成本承诺。每次成功、失败、过期、撤销与清理均写入导出审计。
5. 成功文件和临时文件需按确认后的留存策略自动清理。**建议**成功文件保存 24 小时、失败临时文件在任务结束后立即清理；定时备份频率、保留期限、对象存储位置、跨地域副本和由此产生的费用均尚未确认，不能自行启用。

## 7. Excel 导出与数据库灾备的边界

Excel 全量导出是管理员可查看、离线留档和交叉核验的数据包；它不等同于数据库物理备份，也不能自动证明可恢复生产服务。本阶段明确**不提供 Excel 批量导入**。生产级灾备还需要数据库备份、附件原件存档、密钥管理、恢复权限、恢复演练和恢复目标。

附件二进制原件不随 `.xlsx` 复制；本次只导出第 3 节的附件清单及校验和。是否要求附件原件归档、何处存放及访问保留策略，由 PRODUCT D21 决定。

## 8. 验收与自动核验

备份失败与业务异常必须严格区分。权限不足/撤销、无法建立或保持一致快照、源读取或分页缺失、schema/分片/长文本重组失败、逻辑摘要或行数不一致、文件写入/可打开性失败，均为**备份失败**，不得产生成功文件。配置缺失、业务计算差额、历史悬空引用等为**业务异常**：备份仍应完整完成，`backup_status=COMPLETE_WITH_BUSINESS_ANOMALIES`，并在异常工作表与 `manifest` 中呈现。报表汇总不一致只能使 `report_reconciliation_status` 失败，不能删除原始行或把完整备份降级为空。

每次生成成功文件前，服务端必须完成并记录以下检查：

| 检查 | 通过标准 |
|---|---|
| 快照 | 所有数据集的 `snapshot_id` 与 `as_of` 相同；无读取超出快照的行 |
| 首尾与排序 | 每个分片的首/末主键、分页游标连续，合并后与快照查询的稳定排序一致 |
| 行数 | `manifest` 行数等于源查询行数；分片行数之和等于对应数据集总数 |
| 金额 | 各分配明细按机器精确金额汇总后，写入表3/表7及 `total_amounts` 的核对差异；差异列为业务异常，不能静默四舍五入、补数或掩盖 |
| 引用 | 可解析引用通过引用核对；历史悬空/已删除/缺失引用须保留原始外键并列为业务异常，不得省略该行 |
| 异常任务 | 无法匹配、配置缺失、金额/比例校验失败生成业务异常；导出中权限撤销、快照/分页不完整或文件写入失败才使备份任务失败 |
| 文件可用性 | 每个 `.xlsx` 可打开，工作表/列与 schema 一致，文本、前导零、精确金额和公式转义样例保持预期 |
| 安全 | 非管理员、过期令牌、重复令牌和已撤销角色均无法取得文件；审计可关联请求、下载和清理事件 |

验收样例至少覆盖：零金额和软删除记录、跨月周流水、昵称历史变更、配置版本切换、不同文件分片、超过 15 位文本、以公式字符开头的文本、超过 32,767 字符的审计 JSON/长文本及重组、业务计算差额、配置缺失、历史悬空引用、导出中撤销管理员权限及附件只有清单的情形。D06–D18 未明确的业务计算不在本文件中被推断；其异常应被显式呈现，不能被导出流程吞掉。

## 9. 实施前置条件与待确认边界

- **D20（Excel 导入恢复）**：用户已明确本阶段不需要导入；本规范只定义全量 Excel 导出及完整性核验，不设计恢复接口、导入流程或导入验收。
- **D21（附件）**：待确认附件原件是否需要随备份归档及其存储、访问和恢复要求；当前只导出附件清单。
- **运行策略**：定时任务、文件留存期限、对象存储、费用预算和恢复目标未确认。第 6 节的 15 分钟/24 小时仅为实施建议，不能据此创建定时任务或付费资源。
- **技术选型**：架构方案拟采用 PostgreSQL；本规范要求“一致性快照”这一结果，并计划使用其事务快照能力，见 [PostgreSQL `pg_export_snapshot`](https://www.postgresql.org/docs/current/functions-admin.html)。该方案尚未实现，具体查询、并发边界、压测和恢复演练须在开发阶段验证。

## 10. 与原需求的对应关系

V1.6 第 6.3.1 节授予管理员“所有表查看与导出”权限，第 6.4 节将“报表导出、按月/年查询”放在第四阶段；原文没有规定 Excel、全量范围、历史数据、下载安全、附件、留存或恢复。本契约新增的是管理员的全量 Excel 备份导出实现边界，不改变 F01–F11 的计算公式、数据权限或真实付款规则。
