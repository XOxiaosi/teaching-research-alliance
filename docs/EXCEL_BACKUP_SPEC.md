# 全量 Excel 备份导出技术契约

## 1. 目的、范围与非目标

本文为 F14“管理员全量 Excel 备份导出”提供实现和验收契约。它补足 V1.6 的 F12 中“管理员可查看和导出所有表”未定义的范围、完整性和安全要求，并承接已确认的每周自动备份、财年、账户和多端规则。

- **使用者与入口**：仅“系统管理员”（即平台/系统管理员）可发起、查看全量备份任务及下载文件；老师和公司管理层只能在其授权范围查看资料，不能导出；这不取消已授权的录费、单据或财务业务操作。微信小程序、手机网页和电脑网页的业务规则一致；系统管理员可在各端以该端适合的方式发起异步备份、查看状态和受控下载，不能以手机屏幕或微信入口为由禁止已授权能力。生成始终在服务端完成。
- **全量备份**：按某一确定时点，导出所有业务数据、历史配置和支持理解关联与计算所需的元数据。它不受看板“金额为 0 隐藏”规则影响。
- **按期报表**：按月、年、组织或人员筛选的可读报表，是另一种导出类型；只能包含筛选结果，不能被称为全量备份。
- **非目标**：本文件不生成 `.xlsx`、不接入真实数据，也不提供 Excel 批量导入或恢复生产库的能力。数据库物理灾备、对象存储灾备和恢复演练仍是独立能力。

## 2. 导出类型与管理员操作

| 类型 | 选择条件 | 内容 | 成功条件 |
|---|---|---|---|
| 每周自动全量备份 | 系统调度的当周执行窗口；无业务筛选 | 与手动全量备份相同的全量文件组 | 同一快照、调度幂等和 `manifest` 校验通过 |
| 全量备份 | 无业务筛选；系统记录 `asOf` 时点 | 第 3 节全部工作表、清单和校验信息 | 所有数据集来自同一快照，`manifest` 校验通过 |
| 按期报表 | 月/年、校区、分区、人员等已授权筛选 | 所选报表及其筛选说明；可含必要汇总和明细 | 与界面筛选口径一致，不能替代全量备份 |

手动操作采用异步任务：系统管理员在任一已授权端提交请求后得到任务编号；服务端固定快照、生成文件、执行备份完整性校验，再显示“可下载”。失败任务保留错误码、失败阶段和重试条件，不产生“成功”文件。重新下载同一成功任务不重新取数；重新生成必须创建新的快照和新任务。

### 每周自动调度

- 系统每周五 10:00（北京时间 `Asia/Shanghai`）自动创建一次全量备份，手动全量备份仍保留且不与自动任务互相替代。夏令时不改变北京时间的调度时刻。该调度、成功文件永久留存和历史数据永久留存均已确认；不得将其改为按浏览器时区或按管理员个人会话执行。
- 调度身份为受限的系统任务服务账号，使用最小权限读取快照和写入备份存储，不借用任何个人登录会话、下载令牌或过期凭据。它能生成备份，不能将文件直接发送给个人；每次下载仍按第 6 节重新验权。
- 幂等键固定为 `schedule_id + scheduled_window_start + export_type`。同一执行窗口只能有一个成功文件组；任务超时、可重试故障或进程重启时可安全重试，不能重复产生同一窗口的成功备份或覆盖已成功文件。
- 每次调度保留排队、运行、成功、失败、重试次数、下一次重试时间和最终错误；系统管理员在各端都能看到最近一次和历史执行结果。失败不伪造成功文件，且不得因一次失败跳过后续周任务。

## 3. 全量备份的数据范围

每份全量文件必须含 `00_manifest` 工作表和下表数据。业务表应输出稳定的内部 ID、业务显示名、创建/更新/删除状态、创建人/更新时间与版本号；老师昵称为不可修改的业务标识，不提供昵称改名映射。原始字段、审计 JSON 与长文本均须无损保留，不能仅导出看板可见列。

| 工作表或文件组 | 最低必须内容 | 目的 |
|---|---|---|
| `00_manifest` | 第 4 节字段、工作表清单、各表行数、逻辑摘要、总金额、时区、文件组编号 | 证明本次导出是什么及如何核验 |
| `01_组织、账户与权限` | 组织/校区/分区、个人账户、公司账户、每个校区独立公司账户、老师/公司管理层/系统管理员三类权限角色及逐人职责/范围配置历史（含财务、总负责人全公司范围及管理员财务审批可见权）；九类业务分润身份及其历史分配独立保存；唯一自然人/登录账号/个人钱包映射、管理员角色授予和撤销事件、独立公司钱包归属 | 解释账户归属、权限与分润身份，不能将二者互相替代 |
| `02_表1_教师信息` | 表1所有非秘密原始字段、不可修改昵称、离职/禁登状态、软删除和历史版本 | 还原主数据语义与关联；离职账号禁登但不删除 |
| `03_表2_业务流水` | 表2所有字段、老师/课程下独立学生记录ID及各自字段快照、接收方/输出方、仅供追溯的复制来源、推送/接收状态与业务状态变化、每记录每周累计费用及修订版本、周计划/归属月、21天计时起点/到期及重激活历史；不按同名或真实同一学生合并原始行 | 追溯费用来源和课程流转；没有“拒收”状态 |
| `04_分配明细` | 每笔流水的 `F`、费率、每一分润对象、金额、授课老师剩余、计算资格与排除原因、财年重算批次、改动前/后金额与 `delta`、当时匹配的关系和配置版本 | 使表3/表7可逐笔复核，不能只导出汇总 |
| `05_表3_月度收入` | 表3原始/已发布汇总、期间、财年、汇总版本、重算批次和状态 | 复核月度口径 |
| `06_表4_财务单据` | 三类单据全部字段、审批状态、有效性结果、状态/审批历史与关联附件清单；提现含系统自动通过、提交扣款ledger、待转账/已转账/已撤回/已拒绝、转账办理人及时间、原扣款和唯一返还ledger关联及撤回/拒绝操作者时间 | 复核收入和支出调整 |
| `07_表5_工资奖金` | 已确认发放工资支出与10项奖金收入分列、项目名称版本和历史名称快照（旧记录旧名称、新记录新名称）；每人月度工资计划及有效月份、单月/向后修改范围、历史配置、月生成记录/幂等键、计划修改前后值、实际工资发放/补发确认与扣款ledger、银行卡快照/凭证、修改人和时间（未来计划/待办理与实际支出分开） | 分别核对工资支出与奖金收入 |
| `08_表6_扣费` | 医社保、10 项扣费、项目名称在该行生效的版本、历史名称与调整记录 | 解释扣费总和 |
| `09_表7_费用结算` | 月/年/累计结算快照、各组成项、人工调整净额（提交即生效，不能按审批通过过滤）、余额、跨财年累计余额、财年边界、结算状态和版本 | 复核最终余额；老师仅查看本财年不裁剪管理员全量数据 |
| `10_表8_绩效配置` | 默认比例、按接收方配置、有效时间、操作人、历史版本、复制/批量操作来源 | 解释分配规则的时间点 |
| `11_费率、财年与期间计划` | 基础费率、抬升区间、执行状态、上限、费率历史版本、全财年重算批次、每年 9 月开始的财年、管理员年初生成的全年期间计划、寒暑假整周、管理员锁定的期间归属月、北京时间周二24:00默认截止及管理员延长记录 | 解释实时重算、周与月归属以及跨财年边界 |
| `12_账务调整、审计与调度` | 人工调账ID（财务、管理员及授权开发者）、目标用户账户、调整前/后余额、带符号调整额、必填原因、提交人和时间、关联原单与ledger、上级审批任务/指定审批人、审批状态/意见/时间及完整历史（含待审批）、免审批标记与依据/执行职责（管理员及授权开发者免审）、拒绝/退回的唯一反向冲回ledger、重新提交与原调整的关联；更正/冲销、全财年重算记录、导出任务、每周调度执行与重试、登录外的管理操作审计、审批操作审计、执行人和时间 | 防止只看当前值而丢失变更轨迹 |
| `13_附件清单` | 附件 ID、所属业务 ID、文件名、介质类型、大小、内容 SHA-256、附件版本、`UPLOADING/READY/FAILED` 状态、存储状态和受限访问标识 | 使单据附件可被追溯；清单与原件同时构成全量备份 |

独立学生记录不因姓名相同、复制来源相同或真实为同一人而合并；复制关系只作审计，不能导出成共享学生主记录。未来工资计划应标注计划状态，不计入已入账金额合计；工资已明确线下付后确认扣豆，不能当收入或只按计划扣款；计划在北京时间每月1日00:00生成当月待办，导出分别标明计划月份、生成时间、状态与实付记录。

用户汇总表的零值和非角色项隐藏不影响完整备份：已存的全部身份收入、零值、撤销角色历史及授权审计均保留。个人统一余额只按唯一钱包汇总一次，多个角色视图不能被重复加总；公司钱包独立，明细保留角色/身份归属以解释统一余额。

“删除”不得等同于从全量备份省略：软删除、撤销、拒绝、关闭、历史版本和零金额行均须导出，并以状态列说明。页面为了易读而隐藏零金额项目时，仍须保留机器可读原始行和金额字段。

欢乐豆余额（表7最终余额）允许为负数：负值及负号必须在精确值和展示值中一致保留，不归零、不隐藏，也不单独作为业务异常或导出失败条件。历史业务记录、历史配置、软删除行和软删除行关联的附件原件均永久留存；离职、停用或软删除不能触发销毁。

财年按北京时间从每年9月1日00:00开始，到次年9月1日00:00之前结束。老师的界面只显示本财年，但管理员全量备份必须同时包含所有财年、已锁定的周归属月、跨财年累计余额及历史版本，不能因前端可见范围裁剪。费率规则修改后只实时重算整个当前财年时，备份必须保留重算批次、触发配置版本、原金额、新金额和差额，不能只留下重算后的当前值。

### 首版附件原件与文件包

首版支持发票、付款凭证等业务附件上传，并将附件原件随全量备份下载。一个成功备份文件组由 `.xlsx` 工作簿、`package-manifest.json` 和 `attachments/` 原件目录组成；可作为一个 ZIP 包下载，但 ZIP 只是交付容器，不能替代其中逐文件校验。

- 每份附件在导出快照中必须记录 `attachment_id`、所属业务记录、附件版本、字节大小、介质类型和内容 SHA-256。导出读取的是与同一数据库 `snapshot_id` 对应的附件版本；原件按不可变字节保存，不能在生成中被同名新上传文件替换。
- 以快照内上传状态为准：已完成上传的 `READY` 附件原件全部必需。任一READY原件无法读取、版本不匹配或内容哈希不符，本次备份为**不完整失败**，不得标记成功。上传中 `UPLOADING` 或失败 `FAILED` 的记录完整导出状态及原因，并在清单标为原件未就绪，不能用占位记录、外链或缩略图冒充已备份原件；未形成原件不阻断已存数据的完整备份，也不得将该附件标成已成功备份。
- 首版支持凭证上传，不推定所有单据强制有附件；没有附件的业务记录不因未上传而失败。比例错误、缺少分润收款对象会阻止提交；失败校验审计及已有异常数据仍遵循“原样导出并标异常”的规则。必需附件缺失属于备份内容缺失，不是可带着成功的业务异常。
- `13_附件清单` 的每一条READY版本都必须与 `attachments/` 中一个同哈希原件对应；软删除、作废或历史业务记录的原件仍归档。清单从来不等同于附件原件。

### 业务异常保留原则

全量备份复制的是某一时点的真实已存数据，不是“把数据修正后再导出”的报表。配置缺失、业务金额不平、历史悬空引用、计算差额、旧版本字段不完整和其他业务校验异常，都必须原样导出；同时在 `12_账务调整、审计与调度` 或独立 `14_业务异常` 工作表写出异常编号、涉及记录 ID、规则版本、发现时间和说明。

人工调账提交即生效，待审批记录及关联余额变动必须完整导出；审批状态与入账状态分列，拒绝/退回的反向冲回也单独保留；净额从原调整与冲回账务汇总，不能删除原调整或再次按状态扣一次。上级能随时查阅调整记录不改变系统管理员唯一导出权限。

周录入无需财务确认；校验成功提交的周数据进入计算。比例错误或非零比例缺少收款人会阻止创建/修改，不生成新的有效费用，不影响净额、档位、分润或余额；修改失败保留原成功版本。失败输入和原因作为独立校验审计导出，与有效费用分开、不重复汇总。已有异常数据和历史审计仍原样导出并标明原因，不因正常流程已拦截就省略。

无效、拒绝、作废等业务状态记录同样保留；正常发生的状态本身不等于数据损坏或计算异常。

导出程序不得自动补数、重算覆盖、合并、删除或隐去异常行。备份内容完整不等于业务计算正确：业务校验状态与报表汇总核对状态独立记录，不能因业务异常使全库备份缺行或失败。

### 不导出的秘密与敏感字段

- 密码哈希、密码重置令牌、登录会话、API token、私钥、数据库连接串和任何密钥一律不导出。
- 设计要求管理员获准导出的手机号、银行卡号、开户行、收款户名、发票号等业务字段按原始文本保真；完整业务字段授权已确认，只有系统管理员可以导出，下载、失败和撤销均写入审计记录。
- 卡号与手机号均以文本列保存，不能转为科学计数法、自动去前导零或按公式计算。非系统管理员不可导出已确认；查看时按PRODUCT F01区分完整字段与脱敏范围，业务数据永久留存已确认。

## 4. 快照、清单与一致性

导出任务开始时建立只读一致性快照，所有工作表只能从该快照读取。快照结束后新增或变更的数据进入下一次导出，不能混入当前文件。

`00_manifest` 至少包含：

| 字段 | 含义 |
|---|---|
| `backup_id`、`export_job_id`、`file_group_id` | 本次导出与多文件组的唯一标识 |
| `export_type`、`schedule_id`、`scheduled_window_start`、`schema_version`、`application_version` | 手动/自动导出类型、自动任务执行窗口和字段解释版本 |
| `as_of`、`timezone`、`snapshot_id`、`covered_fiscal_years`、`period_plan_versions` | 固定数据时点、IANA时区、一致性快照、全部覆盖财年及期间计划版本集合 |
| `requested_by`、`requested_at`、`authorization_scope` | 谁在什么权限范围内请求；不记录密码或 token |
| `filters` | 机器可读筛选条件；全量备份显式为“无业务筛选” |
| `sheet_name`、`part_no`、`row_count`、`min_id`、`max_id` | 每个工作表/分片的覆盖范围与行数 |
| `logical_digest`、`total_beans`、`reference_check_result` | 按稳定排序和规范化值计算的逻辑摘要、欢乐豆金额合计和引用检查结果 |
| `fiscal_recalculation_batch_ids`、`rate_version_ids` | 同快照涵盖的全财年重算批次及费率历史版本 |
| `attachment_manifest_digest`、`attachment_ready_count`、`attachment_unready_count` | 附件清单逻辑摘要、可交付原件数量和未就绪数量 |
| `package_manifest_ref` | 外部文件清单的相对路径；完整清单SHA-256仅存任务审计，不写回任何被该清单计算文件哈希的工作簿，避免循环依赖 |
| `generated_at`、`generator_version`、`backup_status` | 生成时间、程序版本和备份完整性状态 |
| `business_validation_status`、`report_reconciliation_status` | 业务异常汇总状态、报表汇总核对状态；二者不决定是否复制原始行 |

导出完成后，服务端生成并随文件组提供只读 `package-manifest.json`，其中列出每个 `.xlsx` 和附件原件的相对路径、文件名、字节 SHA-256、文件大小、工作簿逻辑摘要、附件版本及全组必备分片；服务端任务审计也保存同一清单及其SHA-256，供离线留档时核验文件组是否完整或被改动。工作簿内保存的是各数据集的 `logical_digest`，不把整份文件哈希写回自身，以免形成自引用循环。时区必须使用系统配置的 IANA 名称，并同时作用于 `as_of`、日期时间显示和期间边界；上线前固定该配置，不能由浏览器时区决定。

## 5. Excel 文件格式与大数据策略

Microsoft 规定单个工作表最多 1,048,576 行、16,384 列，单元格最多 32,767 个字符，且数字只有 15 位精度；因此导出不能依赖一个无限大的工作表，也不能把身份证明、精确金额或超长业务资料交给 Excel 自动处理。见已核实可访问的 [Microsoft Excel specifications and limits](https://support.microsoft.com/en-us/excel/excel-specifications-and-limits)。工作表名称还不得超过 31 个字符或含非法字符，见 [Microsoft Rename a worksheet](https://support.microsoft.com/en-us/excel/rename-a-worksheet)。

- 每个工作表最多写入 1,000,000 条数据行（另加标题）；超出时按稳定主键顺序拆为 `03_表2_业务流水_001`、`_002` 等分片。文件整体达到服务端配置的大小或生成时限时，拆分为同一 `file_group_id` 的多个工作簿，每一份都有完整 `manifest`。
- 后台按游标分页读取并流式写出，禁止先把全量记录加载到服务端内存。若技术栈采用 Node.js，ExcelJS 的官方仓库提供 streaming XLSX writer；选型和版本锁定时再以其 [官方文档](https://github.com/exceljs/exceljs#streaming-xlsx) 验证兼容性。
- 文本型 ID、手机号、银行卡号、昵称、发票号、精确金额和比例均以文本写入。所有金额以欢乐豆为结算和展示单位，`1 豆 = 1 元`；输入/入账业务金额两位小数，`*_beans_exact`与`*_beans_display`保留同值及正负号。对计算中间值、历史异常值，另以`*_raw_decimal`无损保留源精度，不得强制截成两位小数；比例同样保存精确文本。不允许Excel自动舍入、科学计数法、归零或改符号，不另设人民币显示金额列。不在文件中放依赖 Excel 的业务公式。
- 所有业务文本显式写为 XLSX 字符串单元格，尤其首字符为 `=`, `+`, `-`, `@` 时禁止写为公式类型，也不插入会改变值的前缀；在 `manifest` 标明 `text_encoding=xlsx_string_v1`。读回值必须与源文本一致，并核验不存在来自业务输入的公式单元格。
- 单元格超过 32,000 个 UTF-16 代码单元的审计 JSON、备注或其他原始长文本，主记录保留 `long_text_ref`，完整文本写入 `14_长文本分片`：`long_text_ref`、源表、源记录 ID、字段名、`part_no`、`part_text`。每片控制在 32,000 个 UTF-16 代码单元内，边界不拆开代理对；按 `part_no` 顺序拼接必须逐字符等于源值；不得截断、摘要或以下载链接替代。若不能新建该工作表、写入任一分片或写入后重组校验失败，备份任务失败，不能降级为截断成功。
- 工作表名、列名、枚举值和字段版本需由导出 schema 注册表统一维护。`sheet_id` 必须是 31 字符以内的合法且唯一技术名，完整中文逻辑名写入 `manifest`；名称冲突或无法分配合法新工作表时任务失败，不能截断名称后覆盖另一工作表。新增列为向后兼容追加，删除或改义必须提升 `schema_version`。

## 6. 生成、下载与留存安全

1. 服务端在手动创建、自动调度开始和开始生成前校验“系统管理员”导出权限；自动调度校验的是系统服务账号授权范围而非个人会话。生成过程若系统管理员权限被撤销则标记对应手动任务失败并删除未完成临时文件；系统调度任务按受限服务账号规则继续受审计控制。
2. “下载”必须经过受控服务端端点：在响应开始前再次校验权限、任务所有权/管理员范围、文件状态和一次性下载令牌。不能把对象存储的长期裸链接交给浏览器。
3. 下载流开始后，系统持续检查撤销标记；角色被撤销时中止尚未完成的传输并审计“已中止”。已经发送到客户端的字节无法收回，此限制必须如实记录。
4. 下载令牌仅可使用一次，并使用短有效期。**建议**有效期 15 分钟；该数值不是当前已确认的保留或成本承诺。每次成功、失败、过期、撤销与清理均写入导出审计。
5. 成功备份文件组（`.xlsx`、`package-manifest.json` 与附件原件）、历史业务数据和历史附件原件永久留存，不设成功文件 TTL 或自动清理。失败任务的临时写入文件可以在诊断信息落库后清理，但不得触碰源业务数据、成功文件组或成功附件原件。短效下载令牌继续独立于永久留存生效。
6. 永久留存会占用持续存储容量；月度运行预算约 300 元是容量、存储策略和告警设计约束，不是“无限免费”的承诺。本轮不采购服务、不部署，也不以预算数字削减已确认的永久留存范围。

## 7. Excel 导出与数据库灾备的边界

Excel 全量导出是管理员可查看、离线留档和交叉核验的数据包；它不等同于数据库物理备份，也不能自动证明可恢复生产服务。本阶段明确**不提供 Excel 批量导入**。生产级灾备还需要数据库备份、附件原件存档、密钥管理、恢复权限、恢复演练和恢复目标。

附件原件随全量备份文件组提供，见第 3 节；但这不等同于数据库物理备份或生产恢复能力。公司管理层的历史资料查看范围尚未明确，本规范不因系统管理员拥有全量备份而扩大其历史访问权限。

## 8. 验收与自动核验

备份失败与业务异常必须严格区分。权限不足/撤销、无法建立或保持一致快照、源读取或分页缺失、schema/分片/长文本重组失败、逻辑摘要或行数不一致、文件写入/可打开性失败，以及快照内READY附件缺少原件、附件版本不属于快照或任一内容哈希不符，均为**备份失败**，不得产生成功文件。配置缺失、业务计算差额、历史悬空引用等为**业务异常**：备份仍应完整完成，`backup_status=COMPLETE_WITH_BUSINESS_ANOMALIES`，并在异常工作表与 `manifest` 中呈现。报表汇总不一致只能使 `report_reconciliation_status` 失败，不能删除原始行或把完整备份降级为空。

每次生成成功文件前，服务端必须完成并记录以下检查：

| 检查 | 通过标准 |
|---|---|
| 快照 | 所有数据集来自同一`snapshot_id`/`as_of`；清单列全覆盖财年和期间计划版本，每行保留其各自版本，不要求不同年份相同；无读取超出快照的行 |
| 首尾与排序 | 每个分片的首/末主键、分页游标连续，合并后与快照查询的稳定排序一致 |
| 行数 | `manifest` 行数等于源查询行数；分片行数之和等于对应数据集总数 |
| 欢乐豆金额 | 各分配明细以两位小数的 `*_beans_exact` 汇总后，写入表3/表7及 `total_beans` 的核对差异；负余额、差异和排除原因均保留，不能静默四舍五入、补数或掩盖 |
| 引用与账户 | 可解析引用通过引用核对；个人/公司账户、校区独立公司账户、三类权限角色和九类分润身份均可按稳定 ID 追溯。历史悬空/已删除/缺失引用须保留原始外键并列为业务异常，不得省略该行 |
| 人工调整 | 调整前余额加带符号调整额等于调整后余额；提交记录、ledger及需审批时的审批任务可追溯；免审记录须明确标记且不伪造审批人/通过事件，待审批不从余额汇总或原始记录中省略；拒绝/退回只冲回一次，重新提交关联新调整与审批，原调整和冲回均保留 |
| 财年重算 | 每个费率版本改变后的当前财年重算批次都有旧值、新值、`delta`、触发版本和期间计划；跨财年累计余额与已锁定月归属可复核 |
| 自动调度 | 每周执行窗口在同一 `schedule_id` 下只产生一个成功备份；重试不产生重复成功组，失败及重试状态对系统管理员可见 |
| 附件原件 | 快照内全部 `READY` 原件与清单一一对应，字节 SHA-256、大小、版本全部匹配；缺原件或哈希不符不能通过。`UPLOADING/FAILED` 记录保留原状态和原因，不能标成原件已备份 |
| 异常任务 | 无法匹配、配置缺失、金额/比例校验失败生成业务异常；导出中权限撤销、快照/分页不完整或文件写入失败才使备份任务失败 |
| 文件可用性 | 每个 `.xlsx` 可打开，工作表/列与 schema 一致，文本、前导零、精确金额和公式转义样例保持预期 |
| 安全 | 老师、公司管理层、过期令牌、重复令牌和已撤销系统管理员均无法取得文件；审计可关联手动请求、自动调度、下载和清理事件 |

验收样例至少覆盖：零金额、负欢乐豆余额、离职禁登和软删除记录、3 周未接收后再次推送激活、跨月周流水、寒暑假整周、管理员锁定归属月、跨财年累计余额、费率全财年重算和 `delta`、个人/校区公司账户、权限角色与分润身份分离、周五 10:00 北京时间自动任务、不同文件分片、超过 15 位文本、以公式字符开头的文本、超过 32,767 字符的审计 JSON/长文本及重组、业务计算差额、比例错误、缺少收款对象、历史悬空引用、自动任务重试、`READY` 发票/付款凭证原件、`UPLOADING/FAILED` 附件、软删除记录的历史原件、附件哈希篡改、导出中撤销系统管理员权限及永久成功文件不被清理的情形。PRODUCT待决定表中尚未明确的业务口径不在本文件中被推断；其异常应被显式呈现，不能被导出流程吞掉。

## 9. 实施前置条件与待确认边界

- **D20（Excel 导入恢复）**：用户已明确本阶段不需要导入；本规范只定义全量 Excel 导出及完整性核验，不设计恢复接口、导入流程或导入验收。
- **D21（自动备份留存与附件）**：已确认每周五 10:00（北京时间）自动全量备份、成功文件/历史数据永久留存，以及首版发票/付款凭证附件上传与原件随备份文件组下载。对象存储实现、容量告警、预算内资源配置和生产恢复目标仍待后续工程细化。
- **运行策略**：系统管理员下载令牌短期有效与成功文件永久留存是不同配置；月度约 300 元预算用于容量核算，不构成部署、采购或无限免费承诺。
- **技术选型**：架构方案拟采用 PostgreSQL；本规范要求“一致性快照”这一结果，并计划使用其事务快照能力，见 [PostgreSQL `pg_export_snapshot`](https://www.postgresql.org/docs/current/functions-admin.html)。该方案尚未实现，具体查询、并发边界、压测和恢复演练须在开发阶段验证。
